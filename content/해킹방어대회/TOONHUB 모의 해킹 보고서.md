**대상** [TOONHUB](https://latest-advocate-poly-algorithm.trycloudflare.com/)  
**과제** 2026년 2학년 2학기 해킹방어대회

## 1. 점검 개요

TOONHUB에서 비로그인 사용자가 제한된 화면에 접근할 수 있는지 확인하고, 공개 검색창에 HTML 태그와 SQL 구문처럼 보이는 문자열을 입력해 응답을 비교했다. 비로그인용 브라우저와 이미 열려 있던 Chrome 세션의 화면을 비교했다. 게시물 작성이나 데이터 수정 없이 점검했다.

## 2. 결과 요약

|번호|점검 항목|실제 관찰|판정|
|---|---|---|---|
|1|비로그인 관리자 페이지 접근 (`/admin`)|`/login?next=/admin`으로 이동|접근 차단 확인|
|2|비로그인 1:1 문의 접근 (`/support`)|`/login`으로 이동|접근 차단 확인|

|4|비로그인 `19` 표시 작품의 회차 열람|1화와 4화 주소 모두 로그인 화면으로 이동|접근 차단 확인|

## 3. 주요 관찰 · `19` 표시 작품의 로그인 후 접근 제어

홈의 인기 랭킹에 `19`가 표시된 작품을 대상으로 같은 회차를 두 브라우저에서 비교했다. 비교 기준으로 홈에 `19` 표시가 없던 다른 작품의 공개 회차도 열었다.

### 재현 절차

1. 로그인하지 않은 브라우저에서 TOONHUB 홈에 접속한다. 랭킹에서 `학생회에도 구멍은 있다!` 카드에 `19` 표시가 있는지 확인한다.
2. 같은 브라우저에서 `/series/학생회에도-구멍은-있다/4`를 연다. 로그인 화면으로 이동하고 URL에 원래 경로가 `next` 값으로 남는지 확인한다.
3. 비교용으로 비로그인 상태에서 `/series/내-최애는-막차를-탄다/91`을 연다. 이 회차는 로그인으로 이동하지 않고 뷰어가 표시됐다.
4. 기존 Chrome 세션에서 2번의 4화 화면을 확인했다. 상단에 이메일 인증을 완료하라는 안내가 표시됐고, 같은 화면에 4화 선택 항목과 1~9페이지 이미지 요소가 있었다. 재현하려면 지정된 테스트 계정에서 이메일 인증 안내가 표시되는 상태로 같은 주소를 연다.

### 관찰 증거

|조건|확인한 화면|
|---|---|
|비로그인 · `19` 표시 작품 4화|`로그인` 화면, `/login?next=/series/…/4`|
|이메일 미인증 안내가 있는 기존 세션 · 같은 4화|`이메일 인증이 아직이에요` 안내 및 4화 뷰어의 이미지 요소 9개|
|비로그인 · 비교 작품 91화|91화 뷰어 및 회차 이미지 요소|

### 영향과 확인 한계

비로그인 요청을 막는 동작과 이메일 미인증 안내가 있는 세션에서 뷰어가 열린 동작을 각각 확인했다. 기존 세션에서 별도의 연령 확인을 이미 마쳤는지는 확인할 수 없었다. 이메일 인증과 연령 확인은 서로 다른 상태이므로, 이 결과만으로 연령 제한을 우회했다고 판정할 수 없다.

제작자가 `19` 표시를 실제 열람 제한으로 사용하고 별도 연령 확인 없이 뷰어와 이미지가 제공된다면, 가입만 한 사용자도 제한 콘텐츠에 접근할 수 있다. 먼저 `19`의 의도와 열람 조건을 확인하고, 연령 확인을 한 적이 없는 새 테스트 계정으로 같은 요청을 재현해야 한다.

### 개선 및 재시험

- `19`를 열람 제한으로 쓰는 경우, 서버에서 로그인과 연령 확인 상태를 함께 검사한다. 작품 페이지와 회차 요청, 이미지 제공 API에 같은 정책을 적용한다. 이메일 인증도 열람 조건으로 정했다면 서버에서 별도로 검사한다. [OWASP 접근 제어 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)
- 비로그인 요청은 로그인으로 이동시키고, 로그인했지만 열람 조건을 충족하지 않은 요청에는 안내 화면이나 `403`을 반환한다. 이미지 저장소가 따로 있다면 권한 검사 후 단기 서명 URL을 발급하는 방식을 검토한다.
- 비로그인, 연령 미확인 테스트 계정, 연령 확인을 마친 테스트 계정으로 같은 회차와 그 이미지 주소를 비교한다. 제한 조건을 충족한 계정에서만 회차와 이미지가 열리는지 확인한다.

## 4. 검색 입력 재현

### HTML 삽입 시험

상단 `작품 · 작가 검색`에 아래 값을 입력하고 검색했다.

```
<b id="toonhub-check">TOONHUB-INPUT-CHECK</b>
```

검색 화면에 꺾쇠와 태그까지 글자로 표시됐고 결과는 0건이었다. DOM에서 `#toonhub-check`도 찾을 수 없었다. 이 시험은 검색어가 출력되는 위치에서 실행 코드 없이 HTML 해석 여부를 확인한 것이다. 댓글이나 게시글에 저장되는 입력은 별도로 시험해야 한다. [OWASP XSS 방어 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)

### SQL 인젝션 시험

|입력|관찰 결과|
|---|---|
|`주술회전`|검색결과 1건|
|`TOONHUB-CHECK'`|검색결과 0건|
|`TOONHUB-CHECK' OR '1'='1`|검색결과 0건|

정상 검색이 작동하는 상태에서 두 입력 모두 결과가 0건이었고, SQL 오류나 전체 목록 반환은 관찰되지 않았다. 검색 기능을 수정할 때 서버에서 매개변수 바인딩을 유지하고, 검색어를 SQL 문자열에 직접 이어 붙이지 않는지 코드에서 확인할 수 있다. [OWASP SQL 인젝션 방어 지침](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)

## 5. 후속 점검 범위

관리자 페이지가 비로그인 요청을 막는 것은 확인했다. 일반 로그인 계정의 관리자 권한 차단, 문의 내역의 계정 간 접근 권한, 글쓰기 API의 서버 검증은 이번 점검에서 확인하지 못했다. 지정된 일반 테스트 계정 두 개를 사용할 수 있다면, 각 계정에 만든 테스트용 문의만 대상으로 다른 계정에서 읽거나 수정할 수 있는지 비교한다.
